## A. Problem of Interest

Robust type systems build safer software. For instance, Rust's memory safety model reduced Google's Android memory vulnerabilities below 20% in 2025 \[1\]. Similarly, Java supports advanced static analysis via the Checker Framework \[2\]. However, developers often avoid advanced type features due to heavy annotation overhead and cognitive burden, which risks producing unsafe code. Conversely, LLM-assisted coding reduces development friction but risks hallucinating vulnerabilities. Combining LLMs with robust type systems bridges this gap: LLMs lower manual overhead, while type systems enforce safety guarantees.

## B. Anticipated Challenges

Our primary goal is to generate type annotations for which:

1. The new types meaningfully prevent domain-specific bugs in practice  
2. Creating and instituting the new annotations do not impose a significant burden for developers

Both are difficult to satisfy. Widely used type annotations like `@NotNull` effectively eliminate common bugs such as `NullPointerException`s, but annotating large legacy codebases requires significant manual effort. Designing these types is also nontrivial for most developers, so domain-specific types are rarely created. Consequently, most practical type annotations remain limited to generic safety checks (e.g. null-safety) rather than domain-specific invariants.

## C. Approach

Our approach will involve a four-step pipeline:

1. Given a bug identified in a codebase, we will classify it into either statically preventable or statically infeasible to prevent.  
* Simple heuristic: Classify bugs involving type conflation (e.g. product vs. customer IDs), unsanitized data, units, or simple range refinements as statically preventable.  
* We may explore more nuanced heuristics that are more accurate and/or reduce manual effort.  
2. If the bug is preventable, prompt an LLM to synthesize Checker Framework annotations and supporting classes/methods (e.g., `AnnotatedTypeFactory`s and coercion/sanitization functions).  
* We will structure prompts modularly to independently request declarations and helper methods, reducing the likelihood of the model omitting an important component.  
* An agentic verification loop ensures the code compiles and passes LLM-generated tests (provides a baseline output quality).  
3. Prompt an LLM harness (e.g., Opencode) to add annotations to relevant codebase sections without modifying executable code. Adherence to this is verified via a deterministic diff sanitizer. The updated codebase should pass standard Java compilation but trigger expected Checker Framework errors.  
* If we find this step has a high failure rate caused by bad annotations/static analysis code (flawed work in the prior step), we may consider retrying the type generation step with feedback about the failure (likely due to either unsatisfiable or trivial checks).  
* If we find this step has a high failure rate due to issues applying annotations (e.g. inability to apply consistent annotations to non-buggy parts of the program), we may consider more complex harnesses. For instance, we may prompt the model one function at a time, with other functions in the callgraph in the context.  
4. Prompt a final LLM to resolve the bug by modifying method bodies while keeping field annotations fixed.  
* This step has the most unknown unknowns: hopefully, the new type annotations will help this last LLM to effectively resolve the bug. We will monitor to determine whether this is true in practice and look for any common failure modes.

We anticipate a few challenges with our approach. For one, the Checker Framework supports custom checkers, which effectively allows the LLM to make its own rules. Furthermore, the Checker Framework supports unsound type features that the LLM may also use. Thus, it is important that we are able to constrain what type designs generated by the LLM are acceptable. Another potential challenge is that even if the LLM generates sound types, they may not be useful for the end user, which is a risk that we will have to minimize as we refine our approach.

## D. Evaluation

1. Find open source projects (e.g. Kafka) on GitHub to test our approach.  
2. Look through commit history for bugs; manually triage them to find places where better static types can help fix them.  
   1. A potential stretch goal will be to have the LLM do the triage.  
3. Run the system on the commit *before* the bug was fixed, with information about the bug (future: without information about the specific bug?)  
4. Check that the final result’s annotations always fail on the old commit and pass on the new (fixed) commit, and that the fix proposed by the LLM after seeing the new types is correct.
